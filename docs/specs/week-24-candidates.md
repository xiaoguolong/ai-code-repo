## 4. 建议的第 24 周范围（现实版）

一周内把 3 个 Agent 都做“完整版”不现实，建议：

### P0（必须）

1. **Agent 2 运营分析**（1.5 天）：读执行记录/审计/token，产出日报与异常列表；
2. **Agent 4 随访**（2 天）：复用审批 + 记忆，新增随访任务表/状态流转；提醒先做站内；
3. **Grafana 口径修正 + 待办积压告警**（0.5 天）；
4. **验收/文档/回归**（0.5 天）。

### P1（时间够再做）

5. **Agent 3 知识库**（1.5–2 天）：**优先包装 enterprise 现有 RAG**，不重复建一套知识库；
   若产品要求平台原生知识库，先只做「查询代理 + 权限/租户校验」，文档管理复用 enterprise。

### P2（明确不做/推迟）

- pgvector 云端迁移、HIS/LIS 真实数据：没有外部条件就不排；
- 平台用户硬删/级联：先做「停用」语义；
- B3 租户自建角色、多级审批、按租户 TTL：留到有真实需求。

> 如果必须“三个 Agent 都出现”，建议 Agent 3 只做**薄接入**（复用 enterprise RAG + 平台权限），
> 把精力放在 Agent 2/4 的端到端验收，而不是三套半成品。

## 5. 第 24 周开始前需要确认

1. **Agent 3 形态**：平台原生知识库 vs 包装 enterprise 现有 RAG？
2. **Agent 4 提醒渠道**：先只做站内待办，还是必须短信/邮件（需要外部网关）？
3. **平台用户生命周期**：停用（推荐，保留审计/外键）还是硬删（需要级联策略）？
4. **pgvector / HIS-LIS**：本周是否有可用扩展与真实数据？没有就明确写「延后」，不占排期。
5. **Agent 2 日报口径**：按租户/按 Agent/按天，面向谁（运营/管理员）？

## 6. 候选验收标准（草案）

- Agent 2：给定时间窗，输出日报（执行量/失败率/token/成本/异常 TopN），数据与
  `execution_record`/指标对得上；租户隔离；无模型时可降级为规则统计。
- Agent 4：HIGH 风险审批通过后生成随访任务；任务可查询/完成/取消；拒绝不生成；
  任务与审批/执行记录可追溯；站内提醒可查。
- Agent 3：复用 enterprise RAG 时，平台侧只做权限/租户校验与答案透传；
  文档列表/问答/引用来源可用；无权限租户不可见。
- 运维收口：Grafana 不再把 `PENDING_APPROVAL` 计入失败率分母；待办积压可告警；
  V6/V7 回滚演练至少做一次。

## 7. 风险

- **范围过大**：3 个 Agent + 收口项会挤在一周；P1/P2 要有明确“可砍”顺序；
- **Agent 3 重复建设**：enterprise 已有 RAG，平台再建一套会造成两套知识库/两套权限；
- **Agent 4 外部通道**：短信/邮件需要供应商与密钥，不能默认为本周范围；
- **pgvector 迁移**：会动云端 PG 镜像/扩展与 `document_chunk`，风险高于普通代码周；
- **当前内存基线**：Langfuse 关闭、OAP 768M，新增 Agent 若常驻大模型/向量服务需重新评估内存。

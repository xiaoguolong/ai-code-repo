# Week 23 阅读提纲 — HITL 与长期记忆生命周期

> 配套实现：`docs/specs/week-23.md`、`notes/impl-logs/week-23.md`
> 目标：把「高风险要人审」「记忆要能管」从口号拆成可落库、可并发、可回滚的工程问题。

## 1. Human-in-the-Loop：先分清「暂停什么」

HITL 不是「弹个确认框」，核心是**在哪个点暂停、状态存在哪、谁能恢复**。

| 暂停点 | 审核人看得到什么 | 代价 |
|--------|------------------|------|
| 模型调用前 | 只有任务描述 | 看不到报告；批准后还要等模型 |
| 工具调用前 | 部分数据 | 看不到完整依据 |
| 报告生成后、副作用前 | 完整报告 + 规则依据 | 一次模型成本已花掉 |

本周选第三种：报告已经生成，但「写随访记忆」这个副作用必须先经人批准。

### 1.1 暂停的实现光谱

1. **进程内内存**：`Thread.sleep` / 内存 Map / `MemorySaver`。重启即丢，不能跨天审批；
2. **图引擎 checkpoint**：Spring AI Alibaba `interruptBefore` + `MemorySaver`（Week 10）；
   语义清晰，但默认仍是进程内，需要换持久化 Saver 才能跨重启；
3. **平台状态机 + 待办表**（Week 23）：执行记录 + `platform_approval`，暂停不占线程，
   审核人隔天/换实例都能处理。

选 3 的理由不是「图引擎不好」，而是**审批是平台级待办**：它要能被列表、被分配、被审计，
不应该只存在于某一次图运行的 checkpoint 里。

### 1.2 状态机与并发

```text
RUNNING ──LOW/MEDIUM──> COMPLETED
RUNNING ──HIGH─────────> PENDING_APPROVAL ──approve──> COMPLETED
                                          └─reject───> REJECTED
```

两个容易写错的地方：

- **先查后改**：两个审核人同时点批准，都查到 `PENDING`，都去写记忆 → 两条随访。
  正确做法是一条 `UPDATE ... WHERE status='PENDING'`，影响 0 行就是抢输，返回 409；
- **决策时重新跑模型**：审核只是「搬运已生成报告 + 写记忆」，重跑会二次计费且报告可能变，
  审核人批的就不是同一份报告了。

### 1.3 幂等与补偿

- 决策接口天然可能被重试（网络超时、用户连点）：状态机 + 409 是幂等边界；
- 「标记已决策 → 写记忆 → 改执行状态」不是单事务：写记忆失败可以只 WARN（与既有口径一致），
  但执行状态写失败会留下「审批 APPROVED、执行 PENDING」的组合，需要日志里的
  `approvalId/executionId` 做人工补偿。强一致需求出现时再引入事务/补偿任务。

## 2. 长期记忆生命周期

### 2.1 TTL 的三种语义

| 做法 | 读取 | 存储 | 问题 |
|------|------|------|------|
| 只定时删 | 删除前仍可见 | 到期后由任务清 | 任务没跑/跑失败就「永生」 |
| 只读时过滤 | 到期立即不可见 | 永远占空间 | 表无限膨胀 |
| **读过滤 + 定期清理**（采用） | 到期立即不可见 | 每日清理 | 需要索引与清理任务 |

关键点：`expires_at IS NULL` 表示「永不过期」，与「过期时间已到」严格区分。
迁移旧数据时把 `expires_at` 留 NULL，才不会一上线误删历史记忆。

### 2.2 删除为什么必须带 scope

`DELETE FROM platform_memory WHERE memory_id = ?` 看起来最简，但它把「隔离」交给了调用方。
正确写法是把隔离谓词写进 SQL：

```sql
DELETE FROM platform_memory
WHERE memory_id = ? AND tenant_key = ? AND user_id = ?
```

删不到时返回 404 而不是 403：403 会告诉攻击者「这条记录存在但不属于你」，
404 不泄露存在性。admin 需要跨用户删除时，也必须显式传目标用户，不能靠「admin 就全表删」。

### 2.3 换 embedding 模型后的旧向量

向量不是「文本的另一种存法」，它绑定模型与维度：

- 模型 A 的 1024 维向量与模型 B 的 1024 维向量**不在同一语义空间**，余弦相似度没有意义；
- 维度不同更糟：余弦计算可能直接报错，或算出看似正常的噪声。

所以需要 `embedding_model = provider:model:dimension` 标记：

1. 保存时写当前标记；
2. 重建时选「标记为空或与当前不同」的记录；
3. 重算后更新向量与标记。

没有这个标记，就只能「清表重来」——第 21 周真机就留下过两条空向量，正是没有标记的代价。

### 2.4 为什么重建是管理端点而不是启动自动跑

- 换模型是低频运维动作，不是每次发布都发生；
- 全量重建会瞬间打满 embedding 配额与请求线程；
- 分批（默认 100、上限 500）+ 返回 `scanned/rebuilt/failed` 让运维可控地推进与重试。

## 3. 观测与审计：别把患者正文写进去

- 待审终态要有独立标签：`execution.status=PENDING_APPROVAL`，否则成功率面板会把「等人审」算成失败；
- 审计只记标识与计数：`approvalId/executionId/memoryId`、`deleted=N/rebuilt=N`，
  **不记任务/报告正文**；
- 审批决策是独立 HTTP 请求，有自己的 traceId；与原始执行通过 `executionId` 关联，
  不伪造父子 span（跨请求的父子关系在链路后端会变成假数据）。

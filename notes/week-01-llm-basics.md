## 0. 本周要建立的心智模型

读完后，必须能用自己的话回答这 6 件事：

| 概念 | 一句话定义 | 工程上为什么重要 |
|------|------------|------------------|
| Foundation Model | 在大规模数据上预训练、可适配多种下游任务的通用模型 | 你不再训模型，而是**适配**现成模型 |
| LLM 工作原理 | 按 Token 自回归预测下一个 Token | 输出是概率采样，不是查表，所以不稳定 |
| Token | 模型真正处理的最小文本单元 | 计费、延迟、上下文长度都以 Token 计 |
| Context Window | 单次请求能塞进去的 Token 上限 | 超了会截断或报错；越长越贵越慢 |
| Prompt Engineering | 用自然语言当接口，控制模型行为 | 最便宜的适配手段，先于 RAG / 微调 |
| 模型调用流程 | Prompt → Tokenize → Prefill/Decode → Detokenize | 聊天接口、日志、Token 统计都挂在这条链上 |

适配手段优先级（全书主线，本周先记住）：

```
Prompt Engineering  →  RAG / Agent  →  Fine-tuning
成本低、迭代快          需要外部知识      最贵、最慢，最后才考虑
```

## 1. 第1章 基于基础模型构建 AI 应用入门

### 1.1 读什么

- 1.1 AI 工程的兴起
- 1.2 基础模型的应用场景
- 1.3 规划 AI 应用
- 1.4 AI 工程技术栈

### 1.2 必须抓住的结论

**AI 工程 ≠ 机器学习工程。**

| | 传统 ML 工程 | AI 工程 |
|--|-------------|---------|
| 核心工作 | 收集数据、训模型 | 选模型、写 Prompt、接工具、做评估 |
| 模型来源 | 自己训 | 用现成基础模型 |
| 瓶颈 | 数据与训练 | 评估、延迟、成本、可靠性 |
| 角色 | ML 工程师为主 | 应用工程师也能做 |

演进路径（1.1）：

```
语言模型 → 大语言模型(LLM) → 基础模型(Foundation Model) → AI 工程
   统计N-gram     规模放大+Transformer    多模态、通用能力      用现成模型做产品
```

基础模型的关键特征：

- 预训练一次，多种任务复用
- 能力来自规模（数据、参数、算力）而不是针对单一任务设计
- 开发者通过 **Prompt / RAG / Tool / 微调** 适配，而不是从零训练

### 1.3 应用场景（1.2）怎么读

不要当产品目录背。按**你计划里会做的**标优先级：

| 场景 | 本学习计划是否会做 | 对应周次 |
|------|-------------------|----------|
| 聊天机器人 | 是 | 第1–2周 |
| 信息聚合 / 知识问答 | 是（RAG） | 第3–4周 |
| 工作流自动化 | 是（Agent Workflow） | 第9–12周 |
| 编程 / 写作 / 教育 | 了解即可 | — |

读每个场景时问一句：**失败了会怎样？**  
聊天答错可以重试；医疗风险分析答错必须有人工审核（第10周 HITL 的伏笔）。

### 1.4 规划 AI 应用（1.3）——本周就要用

做 `spring-ai-demo` 前，先按书里四步写一页纸：

1. **场景评估**：值不值得用 LLM？规则能解决就别上模型。
2. **设定目标**：成功标准是什么？（不能只是「能聊天」）
   - 本周可量化目标：接口可用、请求可追溯、Token 可统计。
3. **里程碑**：先 Demo，再评估，再加记忆 / RAG。
4. **维护**：Prompt 会过时、模型会换、成本会涨。日志和 Token 统计就是为维护做的。

### 1.5 技术栈三层（1.4）——后面 6 个月都按这个分层

```
┌─────────────────────────────────────┐
│  应用层   Chat / Agent / 业务系统     │  ← 你写的 Spring Boot
├─────────────────────────────────────┤
│  编排层   Prompt / RAG / Tool / 评估  │  ← LangChain4j / Spring AI
├─────────────────────────────────────┤
│  模型层   LLM API / 本地推理          │  ← DeepSeek / Qwen / OpenAI
└─────────────────────────────────────┘
```

对照你的计划：

- 第1周：打通应用层 → 模型层
- 第2周：编排层起步（Prompt 模板、结构化输出、上下文）
- 第3周起：编排层加深（RAG / Agent / Workflow）

## 2. 第2章 理解基础模型

本周最硬的一章。目标不是会训模型，而是**调用时知道自己在调什么**。

### 2.1 训练数据（2.1）

记住三句话：

1. 模型能力上限由训练数据决定，Prompt 挖不出没见过的知识。
2. 多语言模型 ≠ 中文一定强；要看中文语料占比。
3. 领域模型（医疗、法律、代码）是数据差异，不是魔法。

对 `spring-ai-demo` 的启示：选 DeepSeek / Qwen 而不是只盯着 GPT，因为中文场景数据更匹配。

### 2.2 建模（2.2）——Transformer 只需理解到调用层

不必手推公式。搞清这几个词：

| 术语 | 含义 | 调用时的影响 |
|------|------|--------------|
| Transformer | 当前主流架构，靠注意力机制建模上下文 | 几乎所有你能调到的 API 都是它 |
| 参数规模 | 7B / 32B / 72B / 更大 | 越大越强、越贵、越慢 |
| 上下文长度 | 8K / 32K / 128K / 1M | 能塞多少历史、文档、工具结果 |
| 开源 vs 闭源 | 权重量不重量 | 要不要自建推理、数据是否出境 |

**Token（本周必懂）**

```
用户输入文本
    ↓ tokenizer（BPE / SentencePiece 等）
Token ID 序列   ← 这才是模型的输入
    ↓ 模型逐 Token 预测
输出 Token ID
    ↓ detokenize
返回文本
```

要点：

- Token ≠ 字 ≠ 词。中文常见约 **1.5–2 字 / Token**，英文约 **0.75 词 / Token**。
- API 按 Token 计费：`prompt_tokens + completion_tokens`。
- 同样一段中文，不同模型的 tokenizer 切出来数量不同，**不要跨模型直接比 Token 数**。
- 特殊 Token（BOS / EOS / 角色分隔符）也占上下文额度。

**Context Window（本周必懂）**

```
[系统提示] [历史消息] [检索到的文档] [用户本轮输入] [模型即将生成]
 |←———————————————— 必须全部塞进 context window —————————————————→|
```

工程含义：

- 超限：截断历史、丢文档、或直接 400。
- 越满：prefill 越慢、越贵。
- 「128K 上下文」不等于「往里塞 128K 效果还好」——书中强调 **context efficiency**，中间的 Token 更容易被忽略（lost in the middle）。

本周实践要求「保存请求日志 + 统计 Token」，就是为了把这两件事从概念变成可观测数据。

### 2.3 后训练（2.3）

预训练只学会「续写」。能对话，靠后训练：

| 阶段 | 做什么 | 你能感知到的结果 |
|------|--------|------------------|
| 监督微调 SFT | 用「指令-回答」对教格式 | 会遵循指令、会当助手 |
| 偏好微调 RLHF / DPO | 用人类偏好排序 | 更礼貌、更安全、更「像人」 |

调用含义：

- 同一个基座，Chat 模型和 Base 模型行为差很远，**聊天接口必须用 Chat / Instruct 模型**。
- 系统提示之所以有效，是因为后训练教过「听系统指令」。

### 2.4 采样（2.4）——聊天接口的调参基础

模型不是输出「正确答案」，而是：

```
对词表中每个 Token 打分（logits）
    ↓ softmax → 概率分布
    ↓ 按策略采样一个 Token
    ↓ 接到后面，再预测下一个
    ↓ 直到 EOS 或 max_tokens
```

必懂参数：

| 参数 | 作用 | 本周建议 |
|------|------|----------|
| `temperature` | 越大越随机 | 聊天 0.7；要稳定事实用 0–0.2 |
| `top_p` | 只从概率累积到 p 的集合里采 | 常用 0.9 |
| `top_k` | 只从分数最高的 k 个里采 | 可先不用 |
| `max_tokens` | 生成上限 | 必须设，防止跑飞烧钱 |
| `stop` | 遇到序列就停 | 多轮对话、JSON 场景有用 |

**推理两阶段（模型调用流程的核心）：**

1. **Prefill**：把整段输入并行算一遍，得到 KV Cache。延迟随输入长度涨。
2. **Decode**：一个 Token 一个 Token 生成。延迟随输出长度涨。

所以：

- 输入很长（大上下文、长历史）→ 首 Token 慢（TTFT 高）
- 输出很长 → 总时长高（TPOT × 输出 Token 数）

**结构化输出（2.4.4）**  
本周了解即可，第2周要做成「返回 JSON」。方法：Prompt 约束、JSON Mode、工具调用、约束解码。越靠后越可靠。

**AI 的概率特性（2.4.5）**  
同一 Prompt 多次调用，结果可以不同。所以必须：

- 记日志（才能复现）
- 统计 Token（才能算成本）
- 后续做评估（第15周），而不是凭感觉调 Prompt

## 3. 第5章 提示工程

本周实践要写聊天接口，Prompt 是你唯一的控制面。

### 3.1 提示词基础（5.1）

**上下文学习（In-context Learning）**

| 方式 | 做法 | 何时用 |
|------|------|--------|
| 零样本 Zero-shot | 只给指令 | 任务简单、模型够强 |
| 少样本 Few-shot | 指令 + 若干例子 | 格式敏感、边界情况多 |

**系统提示 vs 用户提示**

```
system: 你是谁、必须遵守什么、输出格式
user:   这一轮用户真正想做的事
assistant: 模型回复（多轮时会作为历史再喂回去）
```

本周聊天接口至少支持这三种 role。历史消息就是把过去的 user/assistant 再塞进 context window。

**上下文长度 vs 上下文效率**

- 长度：物理上限
- 效率：模型真正用上了多少
- 实践：历史不是越留越多越好；第2周用 Redis 存上下文时，要有截断 / 滑动窗口策略

### 3.2 最佳实践（5.2）——写成你的 Prompt 规范

1. **指令要明确**：角色、任务、约束、输出格式，四件套写全。
2. **给足上下文**：模型看不到你的数据库，除非你放进 Prompt。
3. **拆分复杂任务**：一问多步容易糊；后续 Agent 就是自动化的拆分。
4. **给思考时间**：要求先分析再回答（对推理题有效；对事实题不是万灵药）。
5. **迭代优化**：改 Prompt 必须有固定测试集，否则是在碰运气。
6. **版本管理**：Prompt 当代码看待，不要写死在 Controller 里。  
   → 第2周「Prompt 模板管理」就是这件事。

反例（本周代码禁止）：

```java
// 错误：魔法字符串散落在业务里
chatClient.call("你是助手，请回答：" + userInput);
```

正例方向：

```text
模板文件 / PromptTemplate
  + 变量 {userInput} {history}
  + 版本号
  + 和请求日志一起落库
```

### 3.3 防御性提示工程（5.3）——第14周会系统做，本周先有意识

| 攻击 | 含义 | 本周最低防线 |
|------|------|--------------|
| 越狱 Jailbreak | 诱使模型忽略安全策略 | 系统提示写清边界 |
| 提示注入 Prompt Injection | 用户输入里夹带「忽略上文」 | **永远不要把用户输入当指令拼接** |
| 信息提取 | 套出系统提示或敏感数据 | 系统提示不放密钥、不放内部策略全文 |

本周聊天接口的硬性要求：

- 用户输入当 **数据**，不当代码
- 系统提示与用户内容分离（用 role，不用字符串拼接成一大段）
- 日志可记 Prompt，但 **API Key 禁止入库、禁止打印**

## 4. 模型调用流程（本周实践对照图）

把第1、2、5章收束成你要写的代码路径：

```
客户端
  ↓ HTTP POST /chat  { sessionId, message }
Controller          只做参数校验与鉴权，不写业务
  ↓
ChatService
  1. 取系统提示（模板，带版本）
  2. 取历史消息（本周可先内存/DB，第2周 Redis）
  3. 组装 messages[]：system + history + 本轮 user
  4. 校验总 Token 估算，超出则截断历史
  5. 调用 LLM API
        tokenize（API 侧）
        prefill
        decode
  6. 拿到 content + usage(prompt/completion/total)
  7. 落库：请求日志、Token 记录、消息记录
  8. 返回回复
```

本周完成标准（对照 README）：

- [ ] Spring Boot 项目能启动
- [ ] 能调 DeepSeek / Qwen / OpenAI 之一
- [ ] 有聊天接口
- [ ] 每次调用写请求日志（输入、输出、模型、耗时、状态）
- [ ] 统计 Token（prompt / completion / total）

暂不做（避免 YAGNI）：RAG、Agent、微调、网关、多模型路由。
